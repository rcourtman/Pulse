# v6.2.0 Stable Cutoff Owner Approval

- Decision date: `2026-08-09`
- Release: `v6.2.0`
- Content cutoff base: `b9811cdf538224e7f2870718744300ef8f80afa0`
- Promoted prerelease: `v6.2.0-rc.11`
- Rollback target: `v6.1.2`
- Exact rollback reinstall command: `./scripts/install.sh --version v6.1.2`

## Owner Decision

The release owner directed stable v6.2.0 publication from current `main` and
explicitly waived the remainder of the normal 72-hour soak after
`v6.2.0-rc.11`. This approval covers the current content cutoff and the final
metadata-only release-preparation commit.

This is a one-version owner-risk acceptance, not soak evidence and not a
standing exception for later releases. The changes after the RC11 tag must not
be described as RC-soaked. The workflow input `hotfix_exception=true` carries
this approved waiver through the existing promotion resolver; it does not
reclassify the stable minor release as a patch hotfix.

The exact pushed stable SHA must pass the no-publication `Release Dry Run` and
then be consumed unchanged by the normal single-build release workflow. The
rollback target remains stable `v6.1.2`, using the exact command recorded
above.

## Windows Signing Boundary

Exact-SHA dry run `31306697834` failed closed before candidate assembly or any
public mutation because SignPath reported the `release-signing` policy invalid;
its `Release certificate 2026` CSR remained pending. After that failure, the
release owner explicitly approved a `v6.2.0`-only unsigned-Windows exception so
the stable release can proceed while the external certificate request remains
unavailable.

This is a separate, version-bound decision and is not implied by the soak
waiver. Windows artifacts must remain bound to the exact source SHA and
candidate manifest, checksums, detached `.sig`/`.sshsig` signatures, and
published-digest verification. Public release notes must disclose that the
Windows binaries are not Authenticode-signed and may display an Unknown
Publisher warning. Stable `v6.2.1` and later restore mandatory Authenticode
signing unless another explicit version-bound owner decision is recorded.

## Cutoff Reopen Rule

Only a security defect, data-loss risk, broken upgrade, startup failure, or
release-pipeline defect may reopen v6.2.0. Ordinary product findings and polish
after the cutoff belong in v6.2.1.

## Commercial Boundary

This approval does not authorize production billing mutation or activation of
unproved self-service Relay or Pro plan and cadence transitions. Those paths
remain governed by the existing exposure-safety gate and lane follow-ups.
